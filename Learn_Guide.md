# Part 1. Foundations

## 1. Tabular data

A table is a set of rows (records, here clients or households) and columns (features). Each column has a type, and the type decides which statistics and models make sense:

| Type | Example in RiskSynth | Typical summary | Typical distance |
|---|---|---|---|
| Continuous | `net_income_annual_eur` | quantiles, mean, spread | KS, Wasserstein |
| Discrete numeric | `n_miembros`, `risk_tolerance_score` | counts per value | KS, Wasserstein |
| Nominal categorical | `ccaa`, `primary_investment_goal` | shares | Jensen-Shannon, chi-square |
| Ordinal categorical | `risk_tolerance_category`, `esg_preference_level` | ordered shares | JS, or treat as ranks |
| Boolean | `flag_minimum_investment` | rate | difference in rates |

Why tabular data is harder to generate than images:

- **Mixed types.** One row mixes euros, ages, codes and flags. A single model has to handle all of them.
- **Non-Gaussian marginals.** Income is skewed, debt service is zero for most households and positive for a few. Surplus is negative for 40.9% of EPF households.
- **Hard constraints.** Some combinations are impossible or illegal, not just unlikely: a horizon longer than the client's remaining life, or a "Conservative" label on a score of 9. A generative model learns likelihoods, not rules, so the rules have to be enforced explicitly. That is why RiskSynth has CR01-CR07.
- **Rare but important rows.** The rows that matter most for testing (over-leveraged risk seekers, contradictory questionnaires) are the rarest.

## 2. Synthetic data

Synthetic data is generated by a process instead of being recorded from real entities. Three properties pull against each other:

- **Fidelity**: does it look like the real data (distributions, correlations)?
- **Utility**: does it serve the task? Here the task is testing a robo-advisor's suitability logic.
- **Privacy**: can anything about a real person be learned from it?

Maximum fidelity is copying the real data, which gives zero privacy. Maximum privacy is random noise, which gives zero utility. Every generator sits somewhere between.

Kinds of synthetic data:

| Kind | Idea | In RiskSynth |
|---|---|---|
| Rule-based / simulation | hand-written generative process | rule-based engine (banking payload), and all of stage 2 |
| Resampling | draw real rows, possibly with weights | bootstrap sampler |
| Statistical model | fit a parametric joint distribution | Gaussian copula (SDV) |
| Deep generative model | learn the distribution with a neural network | CTGAN, TVAE (SDV) |
| Hybrid | real or learned base plus derived fields and rules | RiskSynth as a whole |

RiskSynth is a hybrid. Stage 1 produces household demographics and finances grounded in INE data. Stage 2 derives the suitability fields from explicit, documented formulas. A neural network cannot invent suitability answers that INE never measured, so those fields have to be modelled transparently and flagged as `[ASSUMPTION]` until calibrated.

**Privacy in this project.** The inputs are INE public-use microdata files, which INE has already anonymised for public release. No bank or client data is used. The suitability fields are generated. One detail matters for honesty: the bootstrap sampler resamples real (anonymised) EPF household finance blocks, so those numbers are survey records, not newly invented values. The generative SDV engines and the rule-based engine create new combinations. Privacy metrics such as distance to closest record are declared in `model_config.yaml` but not yet computed (see section 26).

## 3. Sampling, survey weights and the bootstrap

**Survey weights.** INE surveys do not sample every household with equal probability. Each record carries a weight, the number of population households it represents. In EPF it is `FACTOR`. Two consequences in the code:

1. EPF money totals such as `GASTMON` are grossed up to the population. Ingestion divides by `FACTOR` to get a per-household figure: `household_expenses_annual_eur = GASTMON / FACTOR`. Before this fix the median "household spending" was about 16.5 million euros.
2. Shares such as "40.9% of households have negative surplus" are weighted by `FACTOR`.

**Bootstrap.** The bootstrap (Efron, 1979) resamples observed rows with replacement. A weighted bootstrap draws each row with probability proportional to its weight, so the sample follows the population, not the survey design. `BootstrapSynthesizer` in `risksynth/generators/client_generator.py` does exactly this on EPF households (`weight_column="peso"`). It creates no new combinations, but it is:

- the fidelity ceiling: hard to beat on marginals and correlations;
- fast, with no SDV dependency;
- a sanity baseline: if a deep model does worse than the bootstrap on fidelity, it is not earning its complexity.

**Hot-deck imputation.** ECV and EPA persons have demographics but no household budget. `resolve_inputs` gives each of them the finance block of a weighted random EPF household from the same cell (10-year age band x employment group), falling back to age band only. This keeps income, spending and mortgage coherent, because they come from one real household, instead of imputing each column separately. Provenance is recorded in `household_finance_source` (`observed` or `donor_epf`).

**Rank (quantile) mapping.** To hit a target mix such as 40/35/18/7% exactly while keeping the ordering a model produces, `quantile_assign` ranks a latent score and cuts it at the cumulative target shares. The lowest 40% become Conservative, the next 35% Moderate, and so on. The model decides who is more risk-tolerant; the config decides how many.

## 4. Copulas

A copula separates a joint distribution into its marginals and its dependence structure. Sklar's theorem: for any joint CDF `H(x, y)` with marginals `F` and `G` there is a copula `C` with

```
H(x, y) = C(F(x), G(y))
```

A Gaussian copula fits as follows:

1. Turn each column into uniforms with its own CDF: `u = F(x)`.
2. Map the uniforms to standard normals: `z = Phi^-1(u)`.
3. Estimate the correlation matrix of the `z` values.
4. To sample: draw multivariate normal `z` with that correlation, then map back: `x = F^-1(Phi(z))`.

Strengths: any marginal shape is preserved exactly, it is fast, and it is easy to explain. Weaknesses: it only captures dependence that a Gaussian correlation can express. It misses tail dependence, where extremes cluster together, and complex conditional structure. SDV's `GaussianCopulaSynthesizer` is the `copula` option in RiskSynth.

## 5. Machine learning refresher

- **Supervised learning** fits `y = f(x)` from labelled pairs. Example: `prob_default` in the rule-based engine.
- **Unsupervised learning** finds structure in `x` alone. Density estimation, learning `p(x)`, is the unsupervised task behind generative models.
- **Loss and optimisation.** A model has parameters, a loss measuring error, and an optimiser (stochastic gradient descent and variants such as Adam) that adjusts the parameters to reduce the loss.
- **Overfitting.** A model that memorises training rows generalises badly. For a generator, overfitting is also a privacy problem: it reproduces real records.
- **Neural network.** Layers of linear maps followed by non-linear activations, trained by backpropagation. Enough width and depth can approximate very complex functions.
- **Latent variable.** An unobserved variable that explains the observed ones. RiskSynth's risk-tolerance model is a hand-specified latent variable: a linear score plus noise, then rank-mapped.

## 6. Generative models: GAN, CTGAN, VAE, TVAE

### GAN

A generative adversarial network (Goodfellow et al., 2014) trains two networks against each other:

- the generator `G(z)` turns random noise `z` into a fake row;
- the discriminator `D(x)` scores how real a row looks.

```
min_G max_D  E_x[log D(x)] + E_z[log(1 - D(G(z)))]
```

The generator improves until the discriminator cannot tell real from fake. Typical problems are mode collapse (the generator produces only a few kinds of rows), unstable training, and no direct likelihood to monitor. Wasserstein GAN with gradient penalty (WGAN-GP) replaces the loss with an estimate of the Wasserstein distance (section 10), which trains more stably.

### CTGAN

CTGAN (Xu et al., 2019, "Modeling Tabular Data using Conditional GAN") adapts GANs to tables:

- **Mode-specific normalisation.** A continuous column with several peaks (income has clusters) is modelled with a variational Gaussian mixture. Each value is encoded as which mode it belongs to plus its normalised position within that mode, so multi-modal columns are not squashed.
- **Conditional generator and training-by-sampling.** For imbalanced categorical columns, training picks a column and a category, then asks the generator for a row with that category. Rare categories are therefore seen often enough to be learned.
- **PacGAN and WGAN-GP** reduce mode collapse and stabilise training.

In RiskSynth, CTGAN is the `ctgan` option, trained on EPF households (`build_stage1_table`). Its output then goes through stages 2 and 3 like every other engine.

### VAE and TVAE

A variational autoencoder (Kingma and Welling, 2013) has:

- an encoder `q(z | x)` that maps a row to a distribution over a latent vector `z`;
- a decoder `p(x | z)` that maps `z` back to a row.

It is trained by maximising the evidence lower bound:

```
ELBO = E_q[log p(x | z)] - KL(q(z | x) || p(z))
```

The first term rewards accurate reconstruction. The second keeps the latent space close to a standard normal prior, so sampling `z ~ N(0, I)` and decoding gives new, realistic rows. The reparameterisation trick (`z = mu + sigma * epsilon`) makes the sampling step differentiable.

TVAE is the tabular VAE from the same CTGAN paper, with the same mode-specific normalisation. It is the `vae` option in RiskSynth. VAEs are usually easier to train than GANs, but their samples can be blurrier, meaning distributions too smooth.

### Choosing between them

| Engine | Fidelity | New combinations | Speed | Dependency |
|---|---|---|---|---|
| Bootstrap | highest on marginals | none (resamples rows) | fastest | none |
| Gaussian copula | good marginals, linear dependence | yes | fast | SDV |
| CTGAN | strong on complex and imbalanced data | yes | slow to train | SDV |
| TVAE | good, smoother | yes | moderate | SDV |
| Rule-based | depends on the rules | yes, plus a banking payload | moderate | none |

## 7. LLMs, diffusion and tabular generation

None of these are used in RiskSynth. They come up in interviews, so know where they sit.

- **LLMs as tabular generators.** GReaT (Borisov et al., 2023) writes each row as a sentence ("age is 42, income is 30000, ...") and fine-tunes a language model on those sentences. Sampling generates new rows and can condition on any subset of columns. Strengths: flexible conditioning and handling of text fields. Weaknesses: slow, numeric precision is weak, and it can memorise training rows.
- **Diffusion models for tables.** TabDDPM (Kotelnikov et al., 2023) learns to reverse a gradual noising process. It is often strong on fidelity, at higher compute cost.
- **Where an LLM could fit this project.** Generating free-text questionnaire answers consistent with a profile, or writing advisor explanations. The numeric suitability logic should stay rule-based and testable. A regulator expects to see why capacity is 6, not a model's opinion.
- **Same evaluation either way.** Whatever generates the rows, the checks in Part 2 apply unchanged: KS, Wasserstein, JS, correlations, rules and assertions.

## 8. Synthetic data as a test harness

A test harness feeds known inputs to a system and checks the outputs against expectations. RiskSynth is built as one for robo-advisors:

- **Known inputs.** Every profile's fields, caps and archetype are recorded.
- **Written expectations.** Each EC01-EC09 archetype carries a `test_assertion`, for example `effective_risk_score <= 5`, and a plain-language `expected_robo_behavior`.
- **Coverage of rare cases.** Quotas guarantee enough rows per archetype (at least 50 per profile at the acceptance threshold) even when the scenario is naturally rare or impossible (EC08).
- **Reproducibility.** A seed and a run contract regenerate the same rows, so a failing test can be replayed.
- **Counterfactuals.** Changing one input and re-scoring (`counterfactual.reassess`) checks that the system responds in the right direction, a form of metamorphic testing.

A useful mental model is property-based testing: instead of hand-writing a few clients, you generate thousands that satisfy stated properties and assert invariants on the advisor's output.

# Part 2. Statistical and financial mechanics

## 9. Kolmogorov-Smirnov distance

For two samples with empirical CDFs `F_n` and `G_m`:

```
D = max over x of | F_n(x) - G_m(x) |
```

It is the largest vertical gap between the two step functions, between 0 (identical) and 1 (no overlap).

Worked example: `a = [10, 20, 30, 40, 50]`, `b = a + 5 = [15, 25, 35, 45, 55]`. Just after x = 10 the CDF of `a` is 0.2 and `b`'s is 0. The gap is never larger, so `D = 0.2` (`scipy.stats.ks_2samp(a, b).statistic`).

How RiskSynth uses it (`fidelity.numeric_tests`):

- It is computed per numeric column against the INE reference, on the base population with injected edge cases excluded.
- It passes when `D <= 0.10`.
- The p-value is reported but not used for pass/fail. With tens of thousands of rows, a tiny, harmless difference gets a near-zero p-value. The effect size `D` is what matters, and the config says so: "p-values are uninformative at n > 50k".

KS is sensitive to differences near the middle of the distribution and weak in the tails. That is why it is paired with Wasserstein.

## 10. Wasserstein distance

The 1-Wasserstein distance (earth mover's distance) is the minimum "mass x distance" needed to move one distribution onto the other. In one dimension it equals the area between the two CDFs:

```
W1 = integral of | F(x) - G(x) | dx
```

For the example above, every point moves by 5, so `W1 = 5.0`.

Unlike KS, W1 is in the units of the data (euros, years), so a 500-euro gap on income and a 5-year gap on age cannot be compared directly. RiskSynth normalises by a robust range of the reference:

```
wasserstein_norm = W1 / (p99_reference - p1_reference)
```

The p1-p99 range is used so one extreme outlier cannot inflate the denominator and hide a real gap. Grades from `model_config.yaml`: below 0.05 excellent, below 0.10 good, below 0.20 acceptable, otherwise poor. A column passes only if KS passes and the grade is not poor.

## 11. Jensen-Shannon divergence and category shares

For categorical distributions `P` and `Q`, with `M = (P + Q) / 2`:

```
JS(P, Q) = 0.5 * KL(P || M) + 0.5 * KL(Q || M)
KL(P || M) = sum_i P_i * log2(P_i / M_i)
```

With base-2 logs, JS lies between 0 and 1. It is symmetric and always finite, unlike KL, which blows up when one side has a category the other lacks. `scipy.spatial.distance.jensenshannon` returns the square root (the JS distance), so the code squares it.

Worked example: `P = (0.5, 0.5)`, `Q = (0.6, 0.4)` gives `JS = 0.0073`, well under the 0.05 limit. But the largest share difference is 10 percentage points. RiskSynth also requires every category to be within 2 pp (`category_share_tolerance_pp`), so this column would fail. JS summarises the whole distribution, and the pp check catches one badly off category that matters to a reader.

## 12. Correlation and dependency checks

Matching each column on its own is not enough: synthetic incomes and synthetic spending can each look right while their relationship is broken.

- **Spearman correlation** is the Pearson correlation of ranks. It captures any monotonic relationship and is robust to skew and outliers, which suits euros.
- **Matrix check** (`fidelity.correlation_tests`): compute the Spearman matrix on the reference and on the synthetic data, subtract them, and look at the off-diagonal absolute differences. It passes when the mean is at most 0.10 and the maximum at most 0.25.
- **Dependency checks** (`dependency_tests`) assert the sign and size of relationships the engine is designed to produce:

| Pair | Expected |
|---|---|
| tolerance vs accepted drawdown | rho >= 0.80 |
| age vs tolerance | rho <= -0.10 |
| age vs horizon | rho <= -0.20 |
| horizon vs liquidity need | rho <= -0.15 |
| income vs investable surplus | rho >= 0.30 |
| tolerance vs capacity | 0.10 <= rho <= 0.70 |

The last row is subtle. Tolerance and capacity must be related but not collinear. If they moved together perfectly, a client could never want more risk than they can bear, and the interesting edge cases (EC01, EC05, EC07) could not exist.

## 13. Household finance: surplus, DSTI, liquid buffer

From `wealth_profile.derive_surplus`:

```
debt_service          = debt_service_annual_eur + consumer_debt_service_annual_eur
raw_surplus_eur       = net_income - household_expenses - debt_service          (signed)
investable_surplus_eur = max(0, raw_surplus_eur)                                (CR06)
surplus_ratio         = raw_surplus_eur / net_income
debt_service_to_income (DSTI) = debt_service / net_income
```

- **Why keep the signed value.** 40.9% of EPF households spend more than they report earning. Flooring at zero for "investable" money is correct, but the negative value is what defines EC04.
- **DSTI.** The share of income that goes to debt payments. The config marks 0.20 as elevated and 0.35 as high (`[EMPIRICAL]`, EPF mortgagors). At 0.35 or more, `CAP_HIGH_DSTI` limits capacity to 5.
- **Liquid buffer.** An emergency fund of three months of spending: `liquid_savings_eur >= 3 * household_expenses_annual_eur / 12`. Below that, `CAP_NO_BUFFER` limits capacity to 6, the EC01 logic.
- **Known bias.** EPF under-reports income relative to its spending diary, which inflates negative surplus. `income_calibration_factor` (default 1.0) multiplies income to correct this once a benchmark (ECV HY020 or tax data) is chosen.

## 14. MiFID II suitability: tolerance vs capacity

MiFID II (Directive 2014/65/EU), Article 25(2), requires a firm giving investment advice or managing portfolios to obtain information on the client's:

- knowledge and experience;
- financial situation, including the ability to bear losses;
- investment objectives, including risk tolerance.

The firm may only recommend what is suitable. Commission Delegated Regulation (EU) 2017/565, Article 54, sets out the detail. Since 2 August 2022, Delegated Regulation (EU) 2021/1253 adds sustainability preferences, which is why RiskSynth records `esg_preference_level`, and why `MIFID_ESG_COLLECTED` checks it is present.

The key idea is that **willingness and ability are different**:

| | Risk tolerance | Risk capacity |
|---|---|---|
| Meaning | how much risk the client wants or can stomach | how much loss the client can afford |
| Source | questionnaire, psychology | finances: surplus, debt, buffer, horizon, job, liquidity |
| RiskSynth column | `risk_tolerance_score` (1-10) | `risk_capacity_score` (1-10) |
| Can change quickly? | yes, with mood and markets | slowly, with circumstances |

A suitable recommendation respects both, so RiskSynth uses `effective_risk_score = min(tolerance, capacity)`. A client who says "Ultra-Aggressive" but has no surplus gets at most 5. A cautious client with ample capacity stays cautious, because capacity never pushes risk above what the client accepts.

## 15. Risk capacity: a full worked example

Client: aged 42, permanent contract, net income 30,000 EUR, spending 24,000 EUR, mortgage 4,800 EUR a year, liquid savings 5,000 EUR, horizon 12 years, liquidity need 20%, stated tolerance 8, accepted drawdown 25%.

**Step 1: surplus and ratios**
- raw surplus = 30,000 - 24,000 - 4,800 = **1,200 EUR**
- surplus ratio = 1,200 / 30,000 = **0.04**
- DSTI = 4,800 / 30,000 = **0.16**

**Step 2: points**

| Input | Value | Band | Points |
|---|---|---|---|
| surplus ratio | 0.04 | 0 to 0.10 | 1 |
| horizon bucket | 12 years | Long | 2 |
| DSTI | 0.16 | below 0.20 | 2 |
| employment | permanent | permanent | 2 |
| liquidity need | 20% | below 50 | 1 |
| **Total** | | | **8** |

**Step 3: caps**
- surplus > 0: no `CAP_NO_SURPLUS`
- DSTI < 0.35: no `CAP_HIGH_DSTI`
- buffer needed = 3 x 24,000 / 12 = 6,000 EUR, and savings are 5,000, so **`CAP_NO_BUFFER` fires (max 6)**
- not Short horizon, liquidity under 50, age under 55: no other caps

`risk_capacity_score = min(8, 6) = 6`, and `effective_risk_score = min(tolerance 8, capacity 6) = 6`.

The engine agrees: `risk_capacity_points = 8`, `risk_capacity_score = 6`, `capacity_caps_applied = CAP_NO_BUFFER`. This client looks like a mild EC01: they earn well enough, but have no emergency fund.

## 16. Model portfolios and the drawdown guard

`risksynth.scoring.robo_advisor` is a deliberately simple, transparent allocator (parameters `[ASSUMPTION]`, in `model_config.yaml -> robo_advisor_simulator`):

- Equity share of the non-cash part by score 1-10: `10, 18, 26, 34, 42, 50, 60, 70, 80, 90` %.
- Cash: at least 3%, otherwise `0.5 x liquidity_need_pct`, at most 60%.
- Stress scenario (2008-style): equities -50%, fixed income -10%, cash 0%.

```
stressed_loss = 0.50 * equity + 0.10 * fixed_income + 0.0 * cash
```

The same client, three allocations:

| Step | Score used | Cash | Equity | Fixed income | Stressed loss |
|---|---|---|---|---|---|
| 1. Tolerance only | 8 (70%) | 3 | 67.9 | 29.1 | **36.9%** |
| 2. + Capacity and liquidity | 6 (50%) | 10 | 45.0 | 45.0 | **27.0%** |
| 3. + Drawdown limit 25% | 6 | 10 | 40.0 | 50.0 | **25.0%** |

Step 3 solves for the equity that makes the loss equal the limit:

```
0.50 * E + 0.10 * (100 - cash - E) = limit
E_max = (limit - 0.10 * (100 - cash)) / (0.50 - 0.10)
      = (25 - 9) / 0.4 = 40
```

If even 0% equity breaches the limit, the excess fixed income moves to cash. Showing three steps lets a reviewer see how much each protection removes. A questionnaire-only advisor (step 1) would expose this client to a loss of about 37% against an accepted 25%.

## 17. Consistency rules CR01-CR07

A raw draw from any generator can produce internally inconsistent profiles. The rules catch them, `consistency.enforce` repairs them, and the row keeps an audit trail.

| Rule | Why it exists | Repair |
|---|---|---|
| CR01 category matches score | labels must follow from the number | recompute the category |
| CR02 drawdown within the category band +/- 2 pp | an Aggressive client accepting 5% loss is a contradiction | clip into the band |
| CR03 horizon bucket matches years | same as CR01 for horizon | recompute the bucket |
| CR04 no Retirement goal at 67+ | already retired | resample the goal, redraw the horizon |
| CR05 horizon <= 90 - age | money needed after expected life is not a real horizon | cap at 90 - age (floor 0.5) |
| CR06 investable = max(0, raw surplus) | arithmetic identity | recompute |
| CR07 Capital Preservation implies horizon <= 5 | long-horizon preservation is a different goal | cap at 5 |

**Repair order** is `CR06, CR04, CR07, CR05, CR03, CR01, CR02`. Order matters because repairs interact. CR04 changes the goal and redraws the horizon, which can create a CR07 or CR05 issue, so those run after it. CR03 recomputes the bucket from the final horizon. CR01 and CR02 come last because they depend on the final score and category. Capacity and effective risk are then recomputed, since they depend on the repaired fields.

**Audit columns**: `cr_violations_raw` (rules the raw draw broke), `cr_repaired` (rules fixed), `profile_inconsistency_flag` (still broken after repair, which only EC08 may be).

**MiFID II checks** run alongside: `MIFID_EFFECTIVE_RISK`, `MIFID_CAPACITY_CURRENT` (stored capacity equals a fresh computation, catching stale values after edits) and `MIFID_ESG_COLLECTED`.

## 18. Edge-case archetypes EC01-EC09

Each archetype has a predicate (who belongs), a quota, an optional capacity cap expected to fire, rules it may relax, and an assertion every member must pass.

| ID | Real-world story | Predicate (short) | Assertion |
|---|---|---|---|
| EC01 | high earner, no buffer after a house purchase | income >= p90, savings < 3 months | effective <= 6 |
| EC02 | young, keen, little money | age 18-30, tolerance >= 8, savings < 5k, surplus < 2.4k, horizon >= 7 | Long horizon or below product minimum |
| EC03 | near retiree chasing growth | age 58-66, growth or retirement goal, Aggressive+, horizon <= 9 | effective <= 7 |
| EC04 | spends more than they earn, wants to invest | raw surplus < 0, tolerance >= 5 | surplus 0 and effective <= 5 |
| EC05 | heavy mortgage, high appetite | DSTI >= p90 of mortgagors, tolerance >= 7 | effective <= 5 |
| EC06 | retiree living off the portfolio | age 67+, income goal, liquidity >= 50% | effective <= 6 |
| EC07 | needs the money soon, wants aggressive | Short horizon, Aggressive+ | effective <= 6 |
| EC08 | contradictory questionnaire | Ultra-Aggressive, drawdown <= 10% | flagged for re-profiling |
| EC09 | valuable home, no free cash (common in Spain) | age 60+, home >= p90, surplus 0 | effective <= 5 |

How the cohort is built (`edge_cases.build_cohort`):

1. Resolve percentile thresholds on the generated population, using EPF fallbacks (for example income p90 = 48,000) for small runs.
2. Compute every predicate on every row, giving `edge_case_matches` (natural prevalence). EC04 matches about 14% of rows on its own.
3. Fill quotas in order of scarcest natural supply first.
4. Take natural matches first, at random.
5. For any shortfall, inject: pick candidate rows outside the cohort, apply a minimal mutation (the "recipe"), recompute capacity, and accept only rows where the predicate holds and no non-relaxed rule breaks. Retry up to 100 times, then report the shortfall.
6. Re-enforce the rules, with exempt rows keeping their relaxed rule. Then evaluate assertions per row.

**Why EC08 is always injected.** CR02 repairs exactly this contradiction in the base population. EC08 is the only archetype with `relaxed_rules: ["CR02"]`, so its rows keep the contradiction and must carry `profile_inconsistency_flag == True`.

**Why EC02 has no cap.** Its expected outcome is that aggressive is suitable, given the long horizon, with small regular contributions. The test checks the horizon or the product minimum, not a cap. Not every edge case means "reduce risk".

Design choices worth defending:

- **Config as the source of truth.** Rules, caps, archetypes, thresholds and simulator parameters live in YAML, with `[EMPIRICAL]` and `[ASSUMPTION]` tags. Code reads them, so recalibration is a config change.
- **One stage-2 path for every engine** (`run_stage2`). Bootstrap, SDV and rule-based outputs share a schema and rules, so the evaluation and the app treat them the same.
- **Engine logic in `src/`, UI in `app/`.** Everything the app shows can be called and tested without Streamlit.

## 21. One profile, end to end

1. `ClientGenerator.fit(build_stage1_table())` learns from EPF households, or `BootstrapSynthesizer` just stores them with weights.
2. `generate()` samples base rows and calls `run_stage2(rows, seed + 1000, cfg)`.
3. `resolve_inputs` makes sure every row has one coherent finance block (observed or hot-deck).
4. `derive_features`, in dependency order:
   - surplus, then liquid savings;
   - goal, given age band, then horizon, given goal, then bucket;
   - latent tolerance, rank-mapped, then drawdown within the category band;
   - liquidity need, then ESG;
   - `compute_capacity`: points, caps, effective risk, product minimum flag.
5. `consistency.validate` records raw violations, then `enforce` repairs and recomputes capacity.
6. `edge_cases.build_cohort` fills EC01-EC09, then rules are re-enforced with exemptions, then `label_and_validate` evaluates assertions.
7. The report records violations raw, repaired, after and exempted, plus edge-case shares and assertion pass rates.
8. In the app, `contract.build` turns parameters, report and frame into `run_contract.json`.
9. `robo_advisor.recommend` gives the three allocations; `fidelity.run_all` compares with INE; `scorecard.edge_case_scorecard` grades the archetypes.

## 22. The workbench code

- `app/streamlit_app.py` registers five pages with `st.navigation(position="hidden")` and draws a custom header from `st.page_link`.
- **Theme.** The Dark/White switch links to `?embed_options=light_theme` or `dark_theme`. `.streamlit/config.toml` defines `[theme.light]` and `[theme.dark]` for Streamlit's own widgets. `portal.theme.mode()` reads the same option, so the CSS tokens and the Altair chart colours change together.
- **Caching.** `portal/data.py` uses `st.cache_data` keyed on the file path and modification time, so a regenerated file is reloaded and unchanged ones are not recomputed.
- **Generation.** `run_generation` calls `contract.generate`, the same function `contract.reproduce` uses, and writes `profiles.parquet`, `profiles.csv`, `run_metadata.json` and `run_contract.json` under `data/synthetic/app_runs/`.
- **Counterfactual inspector.** Each input widget is keyed by client id, so switching client starts from that client's values. Only changed inputs are passed to `counterfactual.reassess`.

## 23. Reproducibility: seeds and run contracts

- **Seeds.** One seed feeds stage 1. Stage 2 uses seed + 1000 and stage 3 seed + 2000 (the `seed_offset` values in `model_config.yaml`). Separate streams mean that changing, for example, the edge-case share does not reshuffle the base population draws.
- **Run contract** (`src/risksynth/contract.py`):
  - `generate(...)` is the single generation path;
  - `build(...)` records parameters, cohort targets and achieved shares, rule counts, config SHA-256 hashes, every `[ASSUMPTION]` line with its YAML key, and a content hash of the profiles;
  - `reproduce(c)` regenerates from the parameters;
  - `verify(c, df)` returns a list of differences (config changed, version changed, row count, columns, content).
- **Content hash.** `frame_sha256` hashes the column names plus a per-row hash of the values cast to strings. Casting makes it robust to dtype changes from a Parquet round trip, but not to value changes. Row order matters, the index does not.

## 24. Presenting the project

A ten-minute walkthrough that works:

1. **The problem (1 min).** Robo-advisors must be tested on many client types, including rare and contradictory ones. Real client files cannot be used freely, and the rare cases are too few anyway.

# Part 4. Questions and answers

## 25. Viva questions

**Data and sources**

**Q1. What problem does RiskSynth AI solve?**
It generates realistic synthetic client risk profiles so robo-advisory and suitability systems can be tested across many client types, including rare and contradictory ones, without using real client data.

**Q2. Why INE data, and why three surveys?**
INE publishes anonymised microdata representative of Spain. No single survey has everything: EPF has household budgets (income, spending, mortgage), ECV has living conditions and demographics, EPA has employment and contract type. Combining them gives demographics and finances grounded in Spanish data.

**Q3. What is `FACTOR` and why divide by it?**
It is EPF's survey weight, the number of population households a record represents. Some EPF money fields are grossed up by it, so the per-household value is the field divided by `FACTOR`. Without this, median spending was about 16.5 million euros.

**Q4. How do ECV and EPA persons get household finances?**
By hot-deck imputation: each gets the full finance block of a weighted random EPF household in the same age band and employment group. Taking a whole block from one household keeps income, spending and debt consistent. Provenance is stored in `household_finance_source`.

**Q5. What is the EFF and why does it matter here?**
The Banco de España's Encuesta Financiera de las Familias, a household wealth survey covering assets, debts and attitudes to financial risk. INE surveys do not measure risk attitudes or liquid savings, so the parameters for those are assumptions. EFF 2022 is the planned calibration source.

**Synthetic generation**

**Q6. Name the stage-1 engines and when you would use each.**
- Bootstrap: highest fidelity, no new combinations, no dependencies; good as a baseline and for quick runs.
- Gaussian copula: fast, preserves marginals, captures linear dependence.
- CTGAN: complex, multi-modal, imbalanced data.
- TVAE: often easier to train than a GAN.
- Rule-based: when a full banking payload (accounts, loans, transactions) is needed.

**Q7. Explain CTGAN in two minutes.**
A conditional GAN for tables. Continuous columns are encoded with mode-specific normalisation (Gaussian mixture modes plus position within the mode). A conditional vector with training-by-sampling makes the generator learn rare categories. Training uses a WGAN-GP style loss with PacGAN to reduce mode collapse.

**Q8. Why not let a neural network generate the suitability fields too?**
INE never measured them, so there is nothing to learn from. They have to be modelled from stated assumptions and enforced by rules. Explicit formulas are also auditable, which matters in a regulated setting.

**Q9. How does the risk-tolerance score hit exactly 40/35/18/7%?**
A latent linear score (age, log income relative to the median, surplus ratio, education, employment, children, goal, horizon, plus noise) is ranked and cut at the cumulative target shares (`quantile_assign`). The model decides the ordering, the config decides the shares.

**Privacy**

**Q10. Is the data private?**
No real client data is used. The inputs are INE public-use files that INE has already anonymised, and the suitability fields are generated. The bootstrap engine does resample real anonymised EPF finance blocks. A production release should add distance-to-closest-record and k-anonymity checks; their thresholds are already in `model_config.yaml`, but they are not computed yet.

**Q11. What is k-anonymity, and what would you use as quasi-identifiers?**
Every combination of quasi-identifiers must be shared by at least k records. The config lists age, sex, region and household size, with k = 5.

**MiFID II logic**

**Q12. What is the difference between risk tolerance and risk capacity?**
Tolerance is the willingness to take risk, from a questionnaire. Capacity is the financial ability to bear losses, from surplus, debt, buffer, horizon, job stability and liquidity need. MiFID II requires both to be assessed.

**Q13. Why is effective risk the minimum of the two?**
A suitable recommendation must respect both limits. If either is low, the lower one binds.

**Q14. How is capacity computed?**
Additive points (surplus ratio 0-3, horizon 0-2, DSTI 0-2, employment stability 0-2, liquidity need 0-1), clipped to 1-10. Then hard caps for no surplus (5), high DSTI (5), no buffer (6), short horizon (6), high liquidity need (6) and near retirement (7). The lowest cap that applies wins.

**Q15. Why caps instead of just points?**
Some situations should limit risk whatever else is true. A household with no surplus should not get a high capacity score just because it has a long horizon and a permanent job. Caps also make the edge-case assertions follow directly from configuration.

**Q16. What is `MIFID_CAPACITY_CURRENT` for?**
It checks the stored capacity equals a fresh computation from the current inputs. That catches stale values after a repair or an edit.

**Rules and edge cases**

**Q17. Give an example of a consistency rule and its repair.**
CR02: the accepted drawdown must lie in the band for the tolerance category, plus or minus 2 pp; an Aggressive client accepting only 5% is contradictory. The repair clips the drawdown into the band.

**Q18. Why does repair order matter?**
Repairs interact. Changing the goal (CR04) redraws the horizon, which can break CR07 or CR05 and change the bucket (CR03). The order runs upstream fields first and recomputes derived ones after.

**Q19. What is the difference between `edge_case_matches` and `edge_case_id`?**
`edge_case_matches` lists every scenario a row satisfies, which is natural prevalence. `edge_case_id` assigns a row to exactly one archetype in the fixed-size test cohort.

**Q20. What does "injected" mean, and why exclude injected rows from fidelity tests?**
When natural matches cannot fill a quota, rows outside the cohort are minimally changed until they satisfy the scenario. They are deliberately over-represented, so including them would distort the comparison with INE. They stay in rule tests.

**Q21. Why is EC08 always injected?**
Its scenario is the contradiction CR02 repairs, so it cannot survive in the base population. EC08 is the only archetype allowed to keep a rule violation, and its assertion is that the profile is flagged for re-profiling.

**Q22. Which archetype does not reduce risk, and why?**
EC02, young with high tolerance and little capital. With a long horizon, an aggressive allocation is suitable. The test checks the horizon or the product-minimum flag instead.

**Evaluation**

**Q23. Why use both KS and Wasserstein?**
KS measures the largest CDF gap, has no units and is sensitive in the middle of the distribution. Wasserstein measures the total shift in data units and is sensitive across the whole range, including tails. Together they catch more kinds of mismatch.

**Q24. Why not use the KS p-value?**
With large samples, trivial differences become statistically significant. The effect size D, with a fixed limit of 0.10, is the meaningful measure.

**Q25. Why normalise Wasserstein by p1-p99?**
To compare columns in different units on one scale, using a range a single outlier cannot inflate.

**Q26. What does the correlation check catch that per-column tests miss?**
Broken relationships, for example correct incomes and correct spending that no longer move together.

**Architecture**

**Q27. Why keep rules and parameters in YAML?**
To separate policy from code. A compliance reviewer can read and change thresholds without touching Python, every value is tagged empirical or assumption, and the run contract hashes the configs.

**Q28. Why does every engine share stage 2?**
So outputs from bootstrap, SDV and rule-based engines have identical schemas and rules, and the same tests and app pages work on all of them.

**Q29. What are the main limitations?**
- `[ASSUMPTION]` parameters are not yet calibrated against EFF 2022.
- EPF under-reports income relative to spending.
- ECV and EPA persons get donated finances.
- Liquid savings are not calibrated.
- Privacy metrics are not implemented yet.
- The simulator portfolios are illustrative.

**Q30. How would you extend the project?**
- Calibrate against EFF 2022.
- Implement DCR, k-anonymity and train-on-synthetic, test-on-real checks.
- Add the ECV household files to fill HY020.
- Add more archetypes through config.
- Connect a real allocation model to the scorecard in place of the simple simulator.

## 26. Technical interview questions

**Testing and CI**

**Q1. How is the test suite organised, and what does `-m "not slow"` do?**
Tests are grouped by module: ingestion, wealth engine, edge cases, generator alignment, robo-testing tools, Streamlit app. `pyproject.toml` registers a `slow` marker for the CLI subprocess and Streamlit AppTest runs. `pytest -m "not slow"` deselects them, so CI gets a fast, deterministic signal. The full suite runs locally.

**Q2. How do you keep expensive fixtures fast?**
Session-scoped fixtures in `tests/conftest.py` run the pipeline once (for example a 20,000-row stage-2 and stage-3 run) and share the result across modules. Outputs go to pytest temporary directories, never into `data/`.

**Q3. How do tests behave when data is missing?**
A `require_processed` fixture skips tests that need the committed parquet files, with a clear message, instead of failing.

**Q4. What does CI do, and what would you add?**
GitHub Actions on every push and pull request to `main`, on Python 3.11 and 3.12: install with `pip install -e ".[dev]"`, run `pytest tests/ -m "not slow"`. Next steps: required status checks, a scheduled job for the slow suite, linting and type-checking gates (black, flake8 and mypy are already dev dependencies), and coverage thresholds.

**Q5. How do you test a Streamlit app?**
With `streamlit.testing.v1.AppTest`: load the script, switch pages, set widget values, click buttons, re-run, and assert on exceptions, rendered markdown and session state. The suite generates a dataset through the UI, checks the run contract verifies, drives the counterfactual sliders and checks the scorecard renders.

**Data formats**

**Q6. Parquet or CSV?**
- Parquet is columnar, compressed and typed. It keeps dtypes such as nullable booleans and categoricals, and reads only the columns you ask for. It is better for pipelines and analytics.
- CSV is universal and human-readable, but untyped.
- RiskSynth has a concrete CSV trap: the ESG category literally named `None` becomes NaN under pandas' default NA list, which is why `risksynth.io.read_profiles` exists. Parquet has no such problem.

**Q7. How do you make a dataset reproducible and prove it?**
Fixed seeds with separate streams per stage, versioned and hashed configs, and a content hash of the output. `contract.reproduce` regenerates and `contract.verify` reports any difference in configs, package version, row count, columns or content.

**Edge-case stress testing**

**Q8. How would you use RiskSynth to test a real robo-advisor?**
1. Generate with the edge-case stress scenario.
2. Feed every profile to the advisor and record its allocation.
3. Compute stressed loss against `max_acceptable_drawdown_pct`.
4. Check each archetype's expected behaviour: EC05 must be de-risked, EC08 must be flagged for re-profiling, EC04 must get no new contributions.
5. Fail the build if any archetype fails, then replay the failure from the run contract.

**Q9. What is metamorphic testing, and how does the counterfactual inspector relate?**
You test relations between outputs instead of exact outputs. For example: raising debt service should never raise capacity; cutting the accepted drawdown should never raise the recommended equity. `counterfactual.reassess` changes one input and re-scores, which is the building block for such tests.

**Q10. How do you guarantee rare cases are covered?**
Quotas per archetype, filled naturally first, then by minimal injection with rejection sampling. The acceptance thresholds require each share within 0.5 pp of target and at least 50 rows per archetype.

**Drift and fidelity**

**Q11. How would you monitor drift between generator versions?**
Run the fidelity suite (KS, normalised Wasserstein, JS, correlation differences) on each new version against the INE reference and against the previous version. Track the metrics over time and alert on threshold breaches. Config hashes in the run contract tell you whether a change came from code or parameters.

**Q12. A column passes KS but fails Wasserstein. What happened?**
Probably a tail difference. KS looks at the single largest CDF gap, often mid-distribution, while Wasserstein accumulates differences across the range. For income, check the top decile.

**Q13. Why can a categorical column pass JS but fail?**
JS summarises the whole distribution and can be small while one category is off by several points. RiskSynth also caps any single category's share difference at 2 pp.

**Production, scaling and calibration**

**Q14. How would you calibrate the `[ASSUMPTION]` parameters?**
1. Take EFF 2022 microdata.
2. Estimate the risk-attitude distribution by age, income and education to set the tier mix and the tolerance coefficients.
3. Estimate liquid deposits by income and age for the savings model.
4. Estimate goal shares by age, where available.
5. Update the YAML, change the tags to `[EMPIRICAL]` with the source, and re-run the fidelity and dependency tests.
6. The run contract's assumption list is the checklist.

**Q15. How would you scale generation to millions of rows?**
- Stage 2 is vectorised pandas, so batch by chunks with independent seed streams.
- Write Parquet partitions.
- Run the rule-based engine with multiprocessing (it already supports `n_jobs` and batches).
- Fit SDV models once and reuse them.
- Move percentile thresholds to a fixed reference so batches stay consistent.
- Compute fidelity on samples.

**Q16. The live app runs on a 1 GB instance. What did you do about memory?**
In-app rule-based runs are capped at 5,000 rows, loaders are cached by path and modification time with bounded entries, and heavy runs are pushed to the CLI.

**Q17. How do you deploy it?**
Streamlit Community Cloud from `app/streamlit_app.py`, or the Dockerfile on Render or Cloud Run: Python 3.12 slim, non-root user, health check on `/_stcore/health`, port from `$PORT`. On Cloud Run, session affinity and a long timeout keep websocket sessions alive.

**Q18. How would you make this auditable for a regulator?**
- It already has config-driven rules with empirical/assumption tags, per-row audit columns (raw violations, repairs, inconsistency flag), written per-archetype assertions, run contracts with hashes, public code with CI, and an HTML evaluation report.
- Add: signed releases, a changelog of parameter changes with sources, and model cards for each stage-1 engine.

**Q19. Where would an ML model add value over rules here?**
In stage 1, learning the joint distribution of demographics and finances (CTGAN or TVAE), and potentially in calibrating the tolerance model from EFF data. The suitability rules and caps should stay explicit, because they encode regulatory logic that must be explainable.

**Q20. What would you test first if the scorecard showed EC05 FAIL?**
1. Check whether the assertion or the data changed: compare config hashes.
2. Check whether `CAP_HIGH_DSTI` fired: look at `cap_fired_pct`.
3. Check the DSTI threshold resolved for the run.
4. Check whether injected rows still meet the predicate after re-enforcement.
5. Then use the counterfactual on a failing row to see which input drives the score.
